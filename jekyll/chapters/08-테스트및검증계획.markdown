## 1) 테스트 계획

각 Python 서비스는 pytest 기반 자동 테스트를 갖는다(2026-09-01 기준).

| 서비스 | 테스트 파일 수 | 주요 검증 대상 |
|---|---|---|
| `apps/api` | 12 | RBAC(N-02), PII 마스킹(N-03, 정량 평가 `test_pii_masking_eval.py` 포함), 딥보이스 데이터셋 회귀(`test_deepvoice_dataset_calibration.py`) + 일반화 검증(`test_deepvoice_generalization.py`) 등 |
| `apps/mcp-server` | 12 | RBAC(`tests/test_rbac.py`), F-01/F-02/F-04/F-07 유스케이스, N-05 동시성 제한(`test_llm_concurrency_limit.py`) |
| `apps/rag-worker` | 3 | 임베딩/pgvector 검색 어댑터 |
| `apps/stt-worker` | 1 | faster-whisper 어댑터 로드/폴백 |

이와 별개로, "판정 알고리즘의 정확도"는 유닛 테스트만으로 검증되지 않으므로 **직접
제작한 합성 데이터셋으로 실측 검증**하는 절차를 따로 둔다.

- **F-01/F-02**: 합성 통화 시나리오 데이터셋으로 카테고리별 정밀도/재현율과 위험도
  스코어 가중치·임계값을 검증했다(`767eac1`).
- **F-03**: 공개 TTS 합성 음성 8건 + LibriSpeech 실제 인간 발화 8건, 총 16건의
  데이터셋으로 딥보이스 판별 임계값을 실측 보정했다(`4b3b0b5`,
  `apps/api/tests/test_deepvoice_dataset_calibration.py`). 임계값을 추측값이 아니라
  실측 통계로 재보정한 결과, 재현율이 0%(원래 임계값 0.01이 16건 전부에서 트리거되지
  않음)에서 87.5%(7/8)로 개선됐다(`deepvoice_adapter.py` 상단 주석 참고). 이후
  v2(wav2vec2) 도입 시 그 16건과 별도인 홀드아웃 48건(TTS 엔진 2종 × 자연 발화
  언어 2종)으로 일반화까지 검증했다(2026-09-01, 전체 47/48 —
  `apps/api/tests/test_deepvoice_generalization.py`).

## 2) 품질 검증 방안 (실측 결과)

문서 내용을 주장으로 남기지 않고, 실제로 떠 있는 서비스에 직접 요청을 보내 확인한
결과를 근거로 남긴다. 아래는 2026-08-31에 mcp-server(`api.service`가 아니라
`mcp-server.service`, 포트 8100)의 N-02 RBAC을 실측한 결과다.

| 케이스 | 기대 | 실측 |
|---|---|---|
| `/health` (키 없음) | 200 (인증 제외 대상) | 200 |
| 키 없음 → `/api/v1/analyze`, `/api/v1/reports` | 401 | 401 / 401 |
| 잘못된 키 → 동일 엔드포인트 | 401 | 401 / 401 |
| VIEWER 키(권한 부족) → 동일 엔드포인트 | 403 | 403 / 403 |
| HANDLER 키 → 동일 엔드포인트 | 200 | 200 / 200 |
| ADMIN 키 → `/api/v1/analyze` | 200 | 200 |

이 과정에서 실제로 이슈 하나를 발견했다 — `/api/v1/reports`를 HANDLER 키로 처음
호출했을 때 500(`psycopg.OperationalError: connection to server at "127.0.0.1", port
5432 failed: Connection refused`)이 발생했다. 조사 결과 RBAC 로직의 문제가 아니라
`vps-postgres` docker 컨테이너가 재부팅 후 내려가 있던 게 원인이었다 — 컨테이너를
재기동하자 정상적으로 200과 함께 신고 접수 응답이 돌아왔다. 이 사례는 "테스트가 초록불이
아니라고 항상 그 기능의 버그는 아니다"라는 걸 실제로 보여준 동시에, **postgres가
mcp-server의 판정/신고 경로 전체를 막는 단일 장애점**이라는 걸 실측으로 확인시켜준
사례라 8장 3절 위험요소에 그대로 반영했다.

N-05(응답 5초 이내 SLA)는 `vps_analysis_duration_seconds` 히스토그램으로 계측
경로를 연결했고(`1414f30`), FastAPI `TestClient`로 `/health`·`/metrics`를 호출해
5개 커스텀 메트릭(`vps_calls_analyzed_total`, `vps_risk_score_distribution`,
`vps_deepvoice_detected_total`, `vps_analysis_duration_seconds`,
`vps_reports_submitted_total`)이 실제로 `/metrics`에 노출되는 것을 확인했다. 다만
이 확인은 "노출되는가"까지이고, "실제 트래픽에서 5초 이내를 만족하는가"는 아직 표본이
쌓이지 않아 별도로 관측해야 한다(8장 3절).

N-01(append-only 감사증적)은 `infra/db/init.sql`의 `reject_audit_log_mutation()`
트리거가 `call_analysis_results`/`report_records` 테이블에 UPDATE/DELETE 시도를
아예 예외로 거부하도록 postgres 레벨에서 강제한다 — 애플리케이션 코드가 실수로
UPDATE 문을 만들어도 DB가 물리적으로 막는 구조라, "코드 리뷰로 막는다"보다 강한
보장이다.

## 3) 위험 요소 및 대응

정직하게 남겨야 할 한계들이다(`docs/design.md` "확장성이 아직 검증 안 된 지점" 및
어댑터 상단 주석 기준).

| 위험 요소 | 내용 | 대응 |
|---|---|---|
| postgres 단일 장애점 | postgres가 내려가면 N-01 감사증적 적재와 F-07 신고 접수가 모두 실패한다(8장 2절에서 실측으로 확인) | `/ready` 헬스체크가 이미 postgres 다운을 503으로 반영함(`d17ba24`). 재기동 자동화(systemd `Restart=` 정책, docker healthcheck)는 TODO |
| F-03 딥보이스 v2의 표본 한계 | v2(wav2vec2 기반 스푸핑 탐지 모델)로 교체했지만 검증 데이터셋이 여전히 16건뿐이고, 모델 카드에 학습 데이터셋이 명시돼 있지 않아 우리 데이터셋과 겹칠 가능성도 배제 못 한다 | v1의 3개 음향 지표를 폐기하지 않고 v2 판정의 보조 근거(N-04)로 계속 반환 — 모델이 틀렸을 가능성을 사람이 대조 확인 가능하게 함(`docs/design.md`) |
| PII 마스킹 v1의 정확도 미검증 | 특히 이름 마스킹은 일반적 성씨+호칭 패턴만 잡아 오탐/누락 가능성이 있음 | 정량 평가 데이터셋 구축 후 재검증 필요 |
| N-05 SLA 실트래픽 미검증 | 메트릭 배선은 완료했지만 실제 부하 상황에서 5초 이내를 만족하는지는 표본 부족 | Grafana 대시보드로 p95/p99 추이 관측 예정 |
| mcp-server 새 진입점(예: gRPC) 확장 미검증 | REST(`rest_server.py`)와 MCP stdio(`server.py`) 진입점 배선 코드가 아직 복붙 상태 | "공유 모듈로 뽑을 만큼 커지면 리팩터링"으로 의도적으로 유보(`rest_server.py` 주석) |
| 실제 통화 데이터 부재 | RFP 제약상 실제 보이스피싱 녹음을 쓸 수 없어, 모든 정확도 지표가 합성 데이터셋 기준 | 데이터 제약은 RFP 자체의 평가 기준("모델 정확도"보다 "판별 근거의 해석가능성")과 일치하므로 의도된 트레이드오프로 명시 |
