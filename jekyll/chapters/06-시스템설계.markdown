## 1) 시스템 구성도

```
frontend (Next.js, 관제 대시보드)
   │
   ▼
api (FastAPI) ──► mcp-server (통화분석/사기패턴DB조회/신고연동 툴) ──► postgres+pgvector
   │                  │                                                   ▲
   │                  └─ Ollama 로컬 LLM (EXAONE 3.5 2.4B, JSON Schema     │
   │                     강제 출력 + 규칙 기반 자동 폴백)                    │
   └──────────────► rag-worker (유사사례 임베딩/검색) ───────────────────────┘
                        │
                        └─ sentence-transformers 로컬 임베딩 모델
                           (jhgan/ko-sroberta-multitask) + 코사인 유사도

stt-worker (faster-whisper, 모바일 오디오→텍스트) ◄── api (F-05 오디오 경로)

prometheus ──► grafana  (애플리케이션 메트릭 관측)
   └─ alerting rule 7종 (N-05 SLA/高위험 급증/LLM 폴백/워커 오류율/생존)
```

5개 서비스로 구성된다.

| 서비스 | 역할 | 담당 요구사항 |
|---|---|---|
| `apps/api` | 탐지 오케스트레이션, 감사증적 적재, RBAC/PII 마스킹 관문 | F-01/F-02/F-05, N-01~N-05 |
| `apps/mcp-server` | 통화분석·사기패턴DB조회·신고연동 도구 분리 (MCP + REST 이원화) | F-01, F-04, F-07, N-02 |
| `apps/rag-worker` | 유사 사기사례 임베딩·검색 | F-04, N-04 |
| `apps/stt-worker` | 모바일 오디오 청크 → 텍스트 변환 | F-05(오디오 경로) |
| `apps/frontend` | 관제 대시보드 | F-06 |

## 2) 헥사고날 아키텍처

`apps/api`, `apps/mcp-server`, `apps/rag-worker` 세 Python 앱 모두 동일한 계층 구조를
따른다(`CLAUDE.md`).

```
domain/          "무엇을 판단하는가" — 프레임워크/DB/외부 API를 전혀 모르는 순수 모델 + 포트
application/     "어떤 순서로 조합하는가" — 유스케이스. domain의 포트에만 의존
infrastructure/  "실제로 어떻게 하는가" — 포트 구현체(어댑터), FastAPI 진입점, DB 연결
```

의존 방향은 `infrastructure → application → domain` 한 방향으로만 흐른다. 이 원칙
덕분에 판정 알고리즘이나 저장소 구현을 통째로 바꿔도 `application/`의 유스케이스
코드는 손대지 않는다 — 이 프로젝트에서 실제로 3개 축(F-01/F-02 판정 알고리즘, F-04
검색 알고리즘, N-01 감사증적 저장소)에서 검증된 내용은 `docs/design.md`(N-06
확장성 설계) 및 7장 2절에 정리했다.

## 3) 통화 분석 파이프라인 설계

텍스트 경로(F-01/F-02)와 오디오 경로(F-05)는 입력 앞단만 다르고 그 뒤 판정 파이프라인은
동일하다.

```
[통화/문자 텍스트]                    [모바일 오디오 청크]
        │                                     │
        │                              stt-worker (faster-whisper)
        │                                     │
        ▼                                     ▼
             apps/api: N-03 PII 마스킹 (전화번호/계좌번호/이름)
                             │
                             ▼
            mcp-server: analyze_call_pattern (F-01/F-02)
              ├─ Ollama(EXAONE 3.5) JSON Schema 강제 출력
              └─ 실패 시 규칙 기반(v1)으로 자동 폴백
                             │
                             ▼
            mcp-server: lookup_fraud_pattern_db (F-04, rag-worker 호출)
              └─ postgres+pgvector 코사인 유사도 검색
                             │
                             ▼
              F-05: 탐지 패턴 + 자연어 설명 + 유사사례를 결합해 판정 근거 생성
                             │
                             ▼
              apps/api: N-01 감사증적(postgres) 적재 + N-05 메트릭 기록
                             │
                             ▼
                  (고위험이면) F-07 신고 접수 mock 호출
```

N-03 마스킹을 mcp-server 호출 **이전**에 넣은 이유는, 판정(F-01/F-02)이 "검찰청 사칭",
"안전계좌로 이체" 같은 문구/패턴에 반응하지 실제 전화번호·계좌번호 자릿수에는 반응하지
않기 때문이다 — 마스킹된 텍스트를 넘겨도 판정 품질에 영향이 없고, PII가 로컬이라도
외부 프로세스(Ollama)로 나가는 것을 원천 차단할 수 있다(`apps/api/src/domain/pii_masking.py`
상단 주석 참고).

## 4) 데이터베이스 설계 개요

감사증적(`call_analysis_results`, `report_records`)과 RAG 검색용 참고 데이터
(`fraud_cases`, pgvector)를 하나의 postgres 인스턴스에 두되 성격을 분리했다 — 감사증적
테이블만 append-only 트리거를 건다. 상세 스키마와 정규화 근거는 부록D 참고.

## 5) 화면 설계 (관제 대시보드)

프론트엔드(Next.js)는 크게 두 화면으로 구성한다.

- **탐지 현황 목록** — 최근 판정된 통화/문자를 위험도 순으로 표시. PII는 기본적으로
  마스킹된 형태(`masked_transcript`)만 노출하고, 원문(`raw_transcript`)은 ADMIN
  권한으로 요청했을 때만 응답에 포함된다(N-02×N-03 결합, `apps/api/src/main.py`의
  `_serialize_call_result` 참고).
- **위험도 분포/처리 통계** — 저/중/고 등급별 건수, 카테고리별(기관사칭/공포조성/
  긴급송금유도/개인정보요구) 탐지 건수 집계.

## 6) 관측성 및 알림 설계

4개 백엔드 서비스가 각자 `/metrics`로 `vps_` 접두사 커스텀 메트릭을 노출하고,
Prometheus가 이를 수집한다(`prometheus/prometheus.yml`). 메트릭을 "보기만" 하는
데서 멈추지 않도록, 요구사항 위반을 직접 판정하는 alerting rule을
`prometheus/alerting/vps-rules.yml`에 둔다.

| 그룹 | 알림 | 조건 | 연결 요구사항 |
|---|---|---|---|
| vps-sla | `VpsAnalysisLatencyP95High` | 판정 소요시간 p95 > 5초 (5분 지속) | N-05 |
| vps-sla | `VpsAnalysisSlaComplianceLow` | 5초 이내 판정 비율 < 90% (15분 창, 10분 지속) | N-05 |
| vps-detection | `VpsHighRiskDetectionSurge` | 최근 10분 高위험 판정률이 직전 1시간 평균의 3배 초과 + 5건 이상 | F-02 |
| vps-detection | `VpsLlmFallbackRateHigh` | Ollama 실패로 규칙 기반(v1) 폴백한 비율 > 20% | F-01 |
| vps-workers | `VpsRagSearchErrorRateHigh` / `VpsSttErrorRateHigh` | 유사사례 검색·STT 오류율 > 10% | F-04 / F-05 |
| vps-availability | `VpsTargetDown` | `vps-*` 스크레이프 대상 2분 이상 응답 없음 | 전체 |

설계 원칙:

- **표본 하한 조건** — 비율 기반 알림에는 모두 "최소 요청 수" 조건을 함께 건다.
  데모 환경은 유휴 시간이 길어 1~2건만 실패해도 오류율 100%가 되기 때문이다.
  高위험 급증도 같은 이유로 "배수 조건 + 절대 건수 5건 이상"을 동시에 요구한다.
- **SLA를 두 축으로 본다** — N-05 부하테스트에서 순차 요청은 SLA를 지켰지만
  동시성 4에서는 94.9%가 위반됐다(8장). p95만 보면 "일부 느린 요청"과 "대부분이
  느린 상황"을 구분하기 어려워, 준수율(5초 버킷 비율)을 별도 critical 알림으로 둔다.
- **k8s 배포** — 규칙 파일은 `prometheus-rules` ConfigMap으로 만들어
  `/etc/prometheus/alerting/`에 마운트한다(로컬 base와 prod overlay 동일).
- **한계** — Alertmanager와 수신 채널(메일/메신저)은 아직 연결하지 않았다. 현재는
  Prometheus UI의 `/alerts`와 `ALERTS` 시계열로만 발화 상태를 확인한다.
