## 1) 보이스피싱 대응의 현황

보이스피싱 수법은 계속 진화하고 있다. 초기의 단순 대출 사기에서 검찰·금융감독원·
금융사기대응센터 등 공신력 있는 기관을 사칭하는 방식으로, 최근에는 가족·지인의 목소리를
흉내 내는 AI 합성 음성(딥보이스)까지 등장했다. 대응 쪽에서는 발신번호 차단, 특정
키워드 기반 스팸 필터링, 사후 신고·수사 등이 주로 쓰이는데, 이런 방식들은 아래와 같은
공통적인 한계를 갖는다.

## 2) 기존 대응 방식의 한계

- **판정 근거가 불투명하다.** 위험도 점수나 "의심" 딱지만 보여주고 왜 그렇게 판단했는지
  설명하지 않는 방식은, 피해자나 상담원이 그 판정을 신뢰하고 즉시 행동할 근거를 주지
  못한다. 오탐(false positive)이 반복되면 사용자가 경고 자체를 무시하게 되는 역효과도
  있다.
- **딥보이스 대응이 비어 있다.** 텍스트/음성 패턴 기반 탐지는 어느 정도 상용화됐지만,
  AI 합성 음성 여부를 판별하고 그 판단 근거까지 사용자에게 보여주는 체계는 아직
  일반화돼 있지 않다.
- **개인정보 처리와 판정 파이프라인이 분리돼 있지 않다.** 통화 내용을 분석하려면
  전화번호·계좌번호·이름 같은 민감정보가 시스템을 통과하게 되는데, 이 과정에서
  비식별화를 어느 단계에 넣을지에 대한 설계가 없으면 분석 정확도와 개인정보 보호가
  서로 트레이드오프처럼 다뤄지기 쉽다.
- **응답이 느리면 무용하다.** 통화가 끝난 뒤 몇 분, 몇 시간 뒤에 판정이 나오면 이미
  피해가 발생한 뒤다. 실시간에 가까운 응답 속도가 전제되지 않으면 탐지 자체의
  실효성이 없다.

## 3) 해결 과제

위 한계들을 이 프로젝트의 요구사항(F-01~F-07, N-01~N-06, `docs/RFP.md` 참고)으로
직접 연결했다.

| 문제 | 대응 요구사항 |
|---|---|
| 판정 근거가 불투명함 | F-05(판정 근거 제시), N-04(설명가능성) — 자연어 설명 + 유사사례(F-04) 근거를 매 판정마다 함께 반환 |
| 딥보이스 대응 공백 | F-03(딥보이스 판별) — 음향 특징 기반 판별기 + 판별 근거(indicator) 반환 |
| 개인정보-분석 파이프라인 미분리 | N-03(개인정보 비식별화) — mcp-server(LLM 포함)에 보내기 *전* 단계에서 마스킹 |
| 응답 지연 | N-05(응답시간) — 통화 종료 후 평균 5초 이내 판정, Prometheus로 SLA 실측 관측 |
| 판정 결과의 무결성 검증 불가 | N-01(감사증적) — append-only DB 트리거로 판정 로그의 사후 변경 자체를 물리적으로 차단 |
| 접근권한 미분리 | N-02(접근통제) — 조회/처리/관리자 3단계 RBAC |
| 신규 사기유형 대응 지연 | N-06(확장성) — 카테고리 enum + 규칙 dict 추가만으로 재설계 없이 확장 |
